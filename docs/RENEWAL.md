# StockInsight 고도화 방향

이 문서는 기존 요구사항을 구현한 서비스를 어떤 사용자 문제에 맞춰 고도화하는지 설명한다.
운영 전환 완료 보고서가 아니라, 현재 구현·디자인 결정·후속 구상을 구분한 문서다.

## 출발점과 근거

- [PRD](./PRD.md)·[TRD](./TRD.md): 기존 조회·저장·비교 흐름과 접근 제어.
- [Figma Persona & Decisions](https://www.figma.com/design/WEmeHbbzBqEfBxez9dMk9o?node-id=23-17): 초기 한지우 페르소나와 화면 결정. 2026-10-26에 내용을 직접 확인했다.
- [PERSONAS](./PERSONAS.md): 2026-10-14에 작성한 확장 페르소나. 기존 Figma 페르소나를 대체한다고 명시한 로컬 문서를 이번 문서 작업에서 저장소에 포함했다.
- [DESIGN](../DESIGN.md)·[UI 기록](./ui/): 코드에 적용한 토큰·화면별 구현과 검증 근거.
- [MIGRATION_STATUS](./architecture/MIGRATION_STATUS.md)·[도메인 경계](./architecture/DOMAIN_BOUNDARIES.md): 서비스 개편의 실제 진행 범위와 미검증 항목.

Figma와 페르소나 문서의 작성 시점·범위는 다르다. Figma 이미지가 최신 페르소나의 모든 기대 기능을 담고 있다고 해석하지 않는다.
페르소나의 사용 시간·저장 규모·시나리오는 설계 가정이며 실측 사용자 조사나 성과 지표가 아니다.

## 기능 범위와 우선순위

### 기존 구현을 보존하는 리뉴얼

종목·키워드 조회와 저장, 조건별 분석, 분석별 오버레이, 정렬·삭제·최신화, 차트·표·다운로드, 사용자 격리와 관리자 읽기 전용 기능을 보존한다.
공통 토큰·셸과 종목 목록·상세·차트부터 개선하고 있다. 화면 구현 범위는 각 [UI 문서](./ui/)와 미병합 PR을 기준으로 판단한다.

Figma의 초기 설계에는 수동 최신화 버튼이 있다. 이를 최신 페르소나의 “자동 갱신” 기대 기능과 같은 것으로 취급하지 않는다.
현재 수동 동작을 제거하거나 자동화가 완료됐다고 문서만으로 선언하지 않는다.

### 확장 페르소나에서 나온 후속 구상

| 구상                             | 해결하려는 문제                   | 구현 전에 필요한 결정                                       |
| -------------------------------- | --------------------------------- | ----------------------------------------------------------- |
| 자동 갱신·주간 요약 메일         | 반복 조회와 이번 주 변화 확인     | 스케줄, 공급자 한도, 비용 상한, 발송 동의와 실패 처리       |
| 관계 높은 종목·키워드 탐색       | 비교 후보를 고르기 어려움         | 통계 정의, 시차·표본·결측, 설명 가능성과 검증               |
| 네이버 데이터 등 공급자 확대     | 국내 테마·세부 조건의 관심도 확인 | 공급자 계약·약관·한도, Google과 다른 지표의 비교 의미       |
| 소셜 인증 확대·온보딩            | 가입과 첫 분석의 진입 부담        | 계정 이전·연결 검증, 공급자 설정, 기존 사용자 복구          |
| 공유 링크·내보내기 정책 개편     | 근거 전달과 원본 데이터 통제      | 공개 범위, 소유권, 만료·철회, 데이터 이용 조건              |
| Kubernetes·GitOps·알림·운영 관측 | 재현 가능한 구축과 1인 장애 대응  | 클라우드 선택, 비용·복잡도, 최소 운영 구성과 장애 수락 기준 |

이 항목들은 현재 제공 기능·승인된 운영 구축·출시 일정이 아니다.
AI 관련 기대가 페르소나에 등장하더라도 RAG는 이번 마이그레이션 범위에 포함하지 않는다.
상관계수·선행 주수는 현재 계산하지 않으므로 기존 화면의 사실처럼 표시하지 않는다.

## 화면과 서비스의 개편은 별개로 검증한다

화면은 저장된 데이터를 어떻게 읽고 탐색하는지 개선한다. 서비스 개편은 인증·소유권·외부 수집·결과 저장의 책임을 나눈다.
예쁜 화면이나 fixture 결과가 실제 데이터 수집·운영 전환 완료를 증명하지 않는다.

- **현재 웹 위치:** 루트 `src/`. `apps/web`로 이동했다고 표시하지 않는다.
- **분석 관리:** 사용자별 저장 데이터와 조건·부모 관계, 작업 세대와 결과 수용을 소유한다.
- **시장 데이터:** 공급자 어댑터와 재사용 가능한 원천 시계열을 소유한다. 공개 원천 데이터의 재사용이 다른 사용자의 저장 분석 접근 권한을 주지는 않는다.
- **worker:** DB나 사용자 토큰을 받지 않고 메시지 계약에 따라 실행한다. 현재 fixture 공급자만 지원한다.
- **인증:** Keycloak/OIDC를 초기 기술 방향으로 선택했다. 기존 owner UUID는 보존하며 이메일만으로 계정을 연결하지 않는다.
- **인프라:** Gateway·Eureka·Redis·RabbitMQ는 업무 컨텍스트가 아니다. 운영 복잡성과 장애 지점이 늘어나는 비용을 함께 다룬다.

## 데이터와 계정을 지키며 전환하기

전환 계획에는 백업, dry-run, 건수·UUID·소유권·부모 관계·표본 계산 비교, 쓰기 전환 시점, 롤백 기준이 필요하다.
기존 비밀번호·OAuth 계정의 투명한 이전 가능성은 미검증이다. 실제 운영 DB 마이그레이션·계정 이전·DNS 변경은 실행하지 않았다.

사용자가 기존 `prod` 데모를 Vercel에 다시 배포한 사실은 기존 서비스 유지에 해당한다.
개편의 클라우드 사업자나 배포 전략을 Vercel로 확정한 것으로 해석하지 않는다.
새 인증 모드에서는 기존 저장 API가 501로 차단되므로 기존 기능의 완전한 대체가 아니다.

## 다음 검증

1. UI별 구현·검증을 마무리하고 실제 저장 데이터로 사용자 흐름을 확인한다.
2. 실제 DB·RabbitMQ·Keycloak에서 인증, 두 사용자 소유권, 중복·재전달·삭제 이후 늦은 결과를 확인한다.
3. 실제 Trends 공급자와 시장 데이터 이관을 TypeScript 계산 기준에 대조한다.
4. 계정 매핑·데이터 이전·비교·전환·롤백을 검증한 뒤 운영 전환을 판단한다.

로컬 Docker 복구는 사용자 지시로 보류 중이다. 위 항목은 자동으로 통과하거나 실행된 것으로 간주하지 않는다.
기존 빌드·E2E 실패와 과거 원격 통과 기록은 [진행 이력](./architecture/MIGRATION_STATUS.md)에 별도로 보존한다.
