# StockInsight ROADMAP

이 문서는 현재 코드 기준으로 앞으로 정리해야 할 작업만 남긴 실행 로드맵이다.

## 우선순위 원칙

1. 사용자 경험이 깨지는 문제 우선
2. 배포 기준 안정성을 유지한 상태에서 개선
3. 구조를 크게 뒤엎기보다, 실제 병목과 불편을 줄이는 방향 우선
4. 문서와 실제 코드의 불일치가 다시 생기지 않도록 작은 단위로 갱신

판단 기준:

- 구조 개선은 사용자 데이터가 섞이거나 저장/복원 흐름이 깨지는 위험을 줄일 때 우선한다.
- UX 개선은 실패 상태, rate limit, 저장 중간 상태처럼 사용자가 바로 체감하는 지점을 우선한다.
- 운영 개선은 장애 원인을 설명할 수 있는 지표부터 추가한다. 특히 cache hit/miss, 외부 API 실패, Python Function 상태는 첫 조회 체감과 장애 진단에 직접 연결된다.
- 테스트는 계산 로직, parser, normalization, 인증/입력 검증처럼 작고 재사용되는 경계부터 시작한다.

## 현재 상태 요약

완료된 기반:

- Supabase Auth/RLS 기반 사용자별 데이터 격리
- 종목 검색, 미리보기, 저장, 상세, 테이블, 최신화, 삭제
- Yahoo Finance 기반 5년 주간 OHLCV 수집
- 키워드 저장, 사전형 목록, 조건별 분석 구조
- Google Trends Python Function 경로
- 키워드 분석별 종목 오버레이 저장/정렬/삭제/최신화
- Excel/PNG 다운로드
- 관리자 읽기 전용 대시보드
- README, PRD, TRD, ROADMAP 기준 문서 최신화

남은 핵심 리스크:

- Trends 첫 조회 체감 속도
- 키워드/분석/오버레이 흐름의 회귀 테스트 부족
- API route와 service/db 책임 분리의 일부 불균일
- 운영 지표가 아직 문제 원인을 충분히 계측하지 못함

## Phase 1. 키워드 분석 UX 마감

목표: 키워드 조회와 저장/복원 경험을 더 분명하게 만든다.

작업:

- 조회 중, 조회 실패, rate limit UI를 유지/개선
- 실패 시 재시도 흐름과 버튼 상태 점검
- 저장 성공/실패, 최신화 성공/실패 토스트 문구 점검
- 키워드 검색/결과/상세 화면의 버튼 배치와 상태 일관성 유지
- 조건 변경 시 분석/오버레이가 바뀌는 맥락을 UI에서 오해 없이 보여주기

수락 기준:

- 키워드 조회 흐름에서 사용자가 현재 상태를 헷갈리지 않는다.
- 실패 시 빈 화면처럼 보이지 않는다.
- 조건별 분석과 오버레이가 섞여 보이지 않는다.

## Phase 2. 성능 체감 개선

목표: 첫 조회와 상세 복원 체감을 구간별로 설명하고 줄인다.

작업:

- 키워드 결과 페이지의 부가 API 호출 필요성 재검토
- Redis hit/miss 기준 로그와 체감 지연 구간 정리
- Trends 조회 경로의 단계별 시간 계측 추가 검토
- cache TTL, prewarm, 경량 DTO 적용 가능성 검토
- 종목 미리보기 Redis 의존성이 UX에 주는 영향 점검

수락 기준:

- “느리다”는 문제를 구간별로 설명할 수 있다.
- 큰 구조 변경 없이 개선 가능한 항목이 분리된다.
- cache hit와 miss의 사용자 체감 차이를 확인할 수 있다.

## Phase 3. API/서비스 구조 정리

목표: 현재 실제 구조를 유지하되, route/service/db 책임 분리를 더 분명히 한다.

작업:

- API route의 공통 순서 점검: 인증, 입력 검증, 서비스 호출, 표준 응답
- route 안에 남아 있는 직접 조합 로직을 service로 이동할지 검토
- `keywords` 계열 API와 `analyses` 계열 API의 역할 경계 재점검
- 인증/응답 형식 공통 처리 일관성 점검
- API_CONVENTIONS와 실제 route method 목록 동기화

수락 기준:

- 주요 API들이 비슷한 패턴으로 읽힌다.
- 새 기능 추가 시 기존 패턴을 재사용할 수 있다.
- API 문서와 route 구현이 충돌하지 않는다.

## Phase 4. 저장 데이터 관리 안정화

목표: 저장된 종목/키워드/분석/오버레이 관리 기능을 회귀 없이 다듬는다.

작업:

- 키워드 상세 최신화/삭제/정렬 흐름 점검
- 분석 삭제 시 오버레이와 시계열 cascade 동작 점검
- 오버레이 최신화 실패 시 기존 데이터 보존 여부 점검
- 종목 상세/미리보기/저장 흐름 점검
- 다운로드 데이터와 파일명 규칙 정리

수락 기준:

- 저장된 데이터 복원, 최신화, 삭제, 다운로드가 회귀 없이 동작한다.
- 실패 중간 상태에서 고아 데이터가 남지 않는다.

## Phase 5. 운영 대시보드 고도화

목표: 운영자가 데이터 수집 문제를 더 빨리 파악할 수 있게 한다.

작업:

- 관리자 대시보드의 이상 후보 기준 보정
- Trends/Python Function 상태 점검을 실제 호출 기반으로 강화할지 검토
- Redis 상태에서 단순 연결 외 hit/miss 지표를 볼 수 있는지 검토
- 최근 분석/오버레이 목록 필터와 정렬 필요성 검토
- `SUPABASE_SECRET_KEY` 미설정 session scope 상태를 더 명확하게 표시

수락 기준:

- 운영자는 최근 수집 실패나 데이터 부족 후보를 빠르게 볼 수 있다.
- 환경 변수 누락과 외부 서비스 문제를 구분할 수 있다.

## Phase 6. 테스트 기반 강화

목표: 핵심 플로우를 자동 검증할 수 있게 만든다.

작업:

- 순수 계산 로직 단위 테스트
- Trends parser와 keyword normalization 단위 테스트
- 인증/입력 검증/API 응답 통합 테스트
- 로그인, 종목 조회, 키워드 조회, 저장, 복원 E2E 스모크 테스트
- 오버레이 추가/정렬/삭제/최신화 회귀 테스트

수락 기준:

- 핵심 회귀를 자동으로 잡을 수 있다.
- 리팩터링 전에 최소한의 안전망이 존재한다.

## Phase 7. 문서 유지

목표: 기준 문서가 다시 코드와 어긋나지 않게 한다.

작업:

- 기능 변경 시 README, PRD, TRD, ROADMAP 중 영향받는 문서만 함께 갱신
- API 변경 시 API_CONVENTIONS 갱신
- Supabase migration 추가 시 TRD 저장 모델 또는 운영 주의점 갱신 여부 확인
- 문서에 미래 희망사항과 현재 구현을 섞지 않기

수락 기준:

- README와 기준 문서가 서로 충돌하지 않는다.
- 문서만 보고도 현재 실행/배포/데이터 구조를 이해할 수 있다.

## 현재 우선순위 요약

1. 키워드 분석 UX 마감
2. Trends/상세 복원 성능 체감 분석
3. API/서비스 구조 정리
4. 저장 데이터 관리 안정화
5. 운영 대시보드 고도화
6. 테스트 도입
